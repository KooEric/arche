# Arche 1.3.0 컬럼 단위 lineage 작업 브리프

2026-11-26 작성. 이 문서는 기억 없이 시작하는 새 Claude 세션을 위한 출발점이다. 새 세션은 이 문서를 읽고 브레인스토밍 → 설계(spec) → 구현 계획(plan) → 구현 순서로 진행한다. 이 문서는 설계가 아니다. 설계 전에 사용자와 정할 질문과, 지금 코드가 실제로 하는 일을 정리한 것이다.

이 문서를 쓴 시점의 기준은 `main` 18cb40d(Arche 1.1.0)이다. 기존 동작을 설명한 부분은 해당 파일을 읽고 적었다. 확인하지 못한 것은 "확인 필요"로 표시했다.

---

## 0. 선행 조건: 1.2.0 위에 쌓는다

1.3.0은 **1.2.0이 `main`에 병합된 뒤의 `main`에서 시작한다.** 1.2.0은 이 문서를 쓰는 시점에 다른 대화에서 설계 중이며, 다음 세 가지를 더한다.

1. dbt 모델을 "그 모델이 쓰는 테이블"로 본다.
2. `schema.yml`·`sources.yml` 메타데이터를 읽는다. 모델·컬럼 설명, 선언된 테스트, 문서화된 컬럼 목록, source의 `schema`·`identifier`가 여기에 들어간다.
3. 리포트에서 문서화된 컬럼과 데이터 컬럼(1.1.0 `profile.json`)을 비교한다.

**1.3.0이 1.2.0에서 가져다 쓰는 것은 정확히 두 가지다.**

| 1.2.0 산출물 | 1.3.0에서의 용도 |
|---|---|
| 문서화된 컬럼 목록(`schema.yml`의 `models[].columns[].name`, `sources[].tables[].columns[].name`) | `SELECT *`를 펼칠 때, 그리고 한정자 없는 컬럼이 어느 소스의 것인지 정할 때 쓰는 **보조 컬럼 목록**. 레포 안 SQL로 컬럼을 알 수 없을 때만 쓴다. |
| dbt 모델 → 테이블 이름 대응(모델 파일이 쓰는 테이블, source의 `schema.identifier`) | dbt 모델 SQL의 출력 컬럼을 어느 테이블의 컬럼으로 기록할지 정하고, `{{ ref('m') }}`·`{{ source('s','t') }}`로 읽은 컬럼을 상류 테이블의 컬럼으로 잇는다. |

1.2.0의 산출물은 [1.2.0 설계](../specs/2026-11-26-dbt-docs-design.md)가 정했다. 모두 `graph.json`의 추가 키이다.

- `dbt_models[]`: `model`, `file`, `table`, `dynamic`, `columns[]`(`name`, `description`, `data_type`, `tests`). `table`은 `{}.orders`나 `{}_marts.orders`처럼 스키마 자리가 변수이다. alias를 리터럴로 알 수 없는 모델은 `dynamic: true`이고 `table`이 없다.
- `dbt_sources[]`: `source`, `table`, `resolved`(실제 테이블 이름 `[database.]schema.identifier`), `columns[]`
- `written_tables[]`의 `via: "dbt:model"` 항목: 모델 파일이 쓰는 테이블
- `source()` 읽기 레코드는 `graph.py`에서 이미 `resolved` 이름으로 바뀌어 있다.

**새 세션은 위 spec과 `docs/artifact-compatibility.md`의 1.2.0 항목을 먼저 읽는다.** 구현 과정에서 키 이름이 바뀌었는지 실제 `main` 코드(`graph.py`의 `dbt_models` 생성부)로 확인한다. 이 문서와 다르면 브레인스토밍의 첫 질문으로 사용자에게 알린다.

**1.2.0 메타데이터가 없을 때.** dbt가 없는 레포(Airflow + SQL/HQL 파일)가 1.3.0의 주 대상이다. 이 경우에도 다음은 그대로 동작해야 한다.

- 컬럼 목록은 레포 안 SQL에서만 얻는다. `CREATE TABLE t (a INT, …)` DDL의 컬럼 정의, 그리고 레포의 다른 SQL이 그 테이블을 쓰면서 만든 출력 컬럼이다.
- 선택적으로 1.1.0 `profile.json`의 데이터 컬럼을 보조 목록으로 쓸 수 있다(결정 질문 Q5).
- 컬럼 목록을 모르는 테이블의 `SELECT *`는 펼치지 않고 `unresolved`(`reason: unknown_star`)로 남긴다.
- dbt 모델은 1.2.0 대응이 없으면 지금처럼 파일 단위 `READS`(`rule: dbt_ref`)까지만 있고, 컬럼 edge의 테이블 이름은 모델 이름(파일 stem)으로 추정한다(결정 질문 Q10).

참고: 1.1.0 data-profile 설계 문서(`docs/specs/2026-11-25-data-profile-design.md`)의 "이후 단계로 미루는 것"은 컬럼 lineage를 1.2에, `INFORMATION_SCHEMA`·실행 로그를 1.3에 두었다. 지금 순서는 그와 다르다(1.2 = dbt 메타데이터, 1.3 = 컬럼 lineage). 새 spec에서 이 변경을 한 줄로 밝힌다.

## 1. 배경과 목표

### 지금 Arche가 하는 일 (1.1.0 기준, 코드로 확인함)

- `langs/sql_tables.py`는 SQL·HQL 텍스트의 주석·문자열·Jinja 블록 태그를 공백으로 가린 뒤(`mask`), `FROM`·`JOIN`·`INSERT INTO`·`INSERT OVERWRITE`·`CREATE … TABLE|VIEW`·`MERGE INTO`·`DELETE FROM` 같은 키워드 뒤의 이름만 읽는다. 모듈 docstring이 스스로 "Not a parser"라고 밝힌다. `SELECT` 목록은 전혀 보지 않는다.
- `{{ ref('m') }}`·`{{ source('s','t') }}`는 가린 텍스트에서 `__dbt_call_N__` 토큰으로 바뀐다. `ref` 읽기는 `dbt_refs`로 따로 모이고, `source('s','t')`는 테이블 `s.t` 읽기가 된다(소문자). source의 `schema`·`identifier` 덮어쓰기는 읽지 않는다(1.2.0이 다룬다). `insert into {{ ref('t') }}`처럼 쓰기 위치의 dbt 호출은 `dynamic` 쓰기(`{}`)다.
- `lineage.py`의 `index`·`resolve`는 읽은 테이블 이름을 쓰는 파일과 맞춘다. 규칙은 `verified`(`rule: name`), `inferred`(`rule: table_name`, 카탈로그 조각 차이나 변수 스키마), `unresolved`(`dynamic`·`ambiguous`), `external`이다.
- `graph.py`의 `_reads`는 파일 → 파일 `READS` edge와 `external_tables`를 만들고, `_written_table_list`는 `written_tables`를 만든다. `_dbt_edges`는 `ref()`를 모델 파일로 잇는 `READS` edge(`rule: dbt_ref`, `via: dbt:ref`)를 만든다.
- `changes.py`는 Git 두 커밋 사이의 **파일 목록**을 얻고(`git diff --name-status`), `IMPORTS`·`REFERENCES`·`READS` 중 `verified`·`inferred` edge를 거꾸로 따라가 영향받는 파일을 BFS로 모은다. 줄 단위 diff는 보지 않는다. `--base-out`을 주면 base 그래프와 head 그래프 양쪽의 영향을 따로 계산한다.
- 1.1.0 `profile.json`은 데이터 폴더의 데이터셋마다 컬럼(이름·타입·null 비율 등)을 기록하고, 데이터셋을 테이블 이름과 맞춘다(`matches`). 리포트의 "Tables" 구역(`report.py`의 `_tables`)이 `report_data.py`의 `table_data`로 테이블별 데이터 상세를 그린다.

### 1.3.0의 목표

두 질문에 **근거 줄과 함께** 답한다.

1. **출처:** 테이블 T의 출력 컬럼 X는 어디서 오는가. 어느 상류 `table.column`에서, 어떤 식(그대로, 이름만 바꿈, 변환, 집계 등)을 거쳐 오는가.
2. **영향:** 테이블 T의 컬럼 C를 바꾸거나 지우면, 어느 하류 컬럼과 SQL 파일과 테이블이 영향을 받는가.

이 답을 세 곳에 낸다.

- 리포트(`report.html`)의 "Tables" 구역
- 새 JSON 산출물(이름은 결정 질문 Q1)
- `changes.py`의 영향 분석(PR 리뷰용): 바뀐 SQL 파일 → 바뀐 컬럼 → 영향받는 하류 컬럼

### 1.1/1.2로는 못 하고 1.3으로 할 수 있게 되는 일

| 사용자 질문 | 1.1/1.2 | 1.3 |
|---|---|---|
| "`mart.revenue.net_amount`는 어디서 계산되나?" | `mart.revenue`를 쓰는 파일까지만 안다. 파일을 열어 직접 읽어야 한다. | `billing.orders.amount`와 `billing.refunds.amount`에서 `SUM(o.amount) - SUM(r.amount)`로 온다. `mart/revenue.sql:14` |
| "`staging.orders.cust_id`를 `customer_id`로 바꾸면 무엇이 깨지나?" | `staging.orders`를 읽는 파일 전체가 영향 후보다(과대 추정). | 그 컬럼을 실제로 참조하는 하류 컬럼 7개, 파일 3개, 테이블 2개. 그중 JOIN 키로만 쓰는 곳 1개는 따로 표시. |
| "이 PR이 컬럼 하나를 지웠는데 리뷰어가 볼 곳은?" | 바뀐 SQL을 읽는 파일 목록 | 지워진 컬럼과, 그 컬럼에 기대는 하류 컬럼·파일 |
| "문서화된 컬럼 중 어떤 SQL도 만들지 않는 것은?" | 1.2가 문서 vs 데이터를 비교 | 문서 vs SQL 출력 컬럼도 비교 가능(선택 범위, Q11) |

## 2. 범위 / 하지 않는 것

### 이번 범위 (in scope)

- `SELECT` 목록: 컬럼 참조, 별칭(`AS x`, `AS` 없는 별칭), 식(`a + b`, 함수 호출, `CAST`, `CASE`), 집계(`SUM`, `COUNT` 등), 윈도 함수(`… OVER (PARTITION BY … ORDER BY …)`)
- 한정자: `t.col`, `alias.col`, `schema.table.col`. JOIN에서 별칭으로 소스를 구분한다.
- CTE: `WITH a AS (…), b AS (…)` 체인, 열 목록이 있는 CTE(`WITH x (c1, c2) AS (…)`), `WITH RECURSIVE`(재귀 부분은 비재귀 부분의 컬럼만 따른다)
- `FROM`·`JOIN` 안의 서브쿼리(파생 테이블)와 그 별칭, 스칼라 서브쿼리(`SELECT (SELECT max(x) FROM t) AS m`)
- `UNION [ALL]`, `INTERSECT`, `EXCEPT`: 위치(순서)로 컬럼을 맞춘다. 이름은 첫 분기의 것이다.
- 쓰기 형태
  - `INSERT INTO|OVERWRITE [TABLE] t (c1, c2) SELECT …`: 열 목록과 위치로 맞춘다.
  - `INSERT … t SELECT …`(열 목록 없음): 대상 테이블 컬럼 목록을 알면 위치로, 모르면 SELECT 별칭으로 추정한다(Q7).
  - `CREATE [OR REPLACE] TABLE|VIEW t AS SELECT …`
  - `CREATE TABLE t (c1 type, …)` DDL: 컬럼 목록만 기록한다(edge 없음).
  - Hive `FROM src INSERT OVERWRITE TABLE t SELECT …`(다중 INSERT): 지금 `sql_tables`가 이 형태를 읽으므로 지원 대상에 넣는다. 범위가 크면 Q-목록에서 미룰 수 있다.
- dbt 모델: 파일 전체가 `SELECT` 하나이고, 출력 테이블은 모델(1.2.0 대응)이다. `{{ ref() }}`·`{{ source() }}`는 테이블 자리로 본다.
- `SELECT *`, `t.*`: 소스 컬럼 목록을 알 때만 펼친다. BigQuery `* EXCEPT (…)`, `* REPLACE (…)`, Snowflake `* EXCLUDE (…)`, `* RENAME (…)`의 기본 형태.
- WHERE·JOIN ON·GROUP BY·HAVING·QUALIFY에 쓰인 컬럼: 출력 컬럼을 만들지는 않지만 "이 컬럼을 지우면 깨지는 곳"이므로 기록한다(Q4의 `filter`, `join_key`, `group_key`).
- `MERGE INTO t USING s ON … WHEN MATCHED THEN UPDATE SET c = s.x WHEN NOT MATCHED THEN INSERT (c) VALUES (s.x)`: 기본 형태만. 범위가 크면 미룬다(Q-목록 참고).

### 하지 않는 것 (out of scope)

- 저장 프로시저, `DECLARE`·`BEGIN … END` 블록, 절차형 SQL(PL/SQL, T-SQL, BigQuery scripting)
- 동적 SQL(`EXECUTE IMMEDIATE`, 문자열로 만든 쿼리)
- UDF 본문. UDF 호출은 "변환"으로만 본다. 인자 컬럼 → 결과 컬럼 edge는 남기되, 함수 안을 따라가지 않는다.
- `PIVOT`·`UNPIVOT`: 출력 컬럼이 데이터 값으로 정해진다. 발견하면 그 SELECT를 `unsupported`로 남긴다.
- Python 문자열 안의 SQL(Airflow 오퍼레이터의 `sql="…"`). 테이블 lineage도 읽지 않는 영역이다.
- 레포 밖에서 정의된 뷰 펼치기. 테이블 lineage가 뷰 안을 따라가지 않는 것과 같다.
- `USE db;`로 정해지는 기본 스키마(테이블 lineage와 같음)
- `UPDATE t SET …`, `ALTER TABLE … ADD|RENAME COLUMN`. ALTER로 컬럼 이름이 바뀌는 것은 추적하지 않는다. 발견하면 리포트 안내문에 한계로 적는다.
- 구조체 필드·배열 원소 단위 lineage(`a.b.c`가 구조체 필드 경로인 경우, `LATERAL VIEW explode(arr)` 결과의 필드). 구조체 접근은 최상위 컬럼까지만 잇는다.
- Jinja `{% for %}`로 컬럼을 만드는 모델, `dbt_utils.star()`·`dbt_utils.pivot()` 같은 매크로의 결과 펼치기. `unresolved`(`reason: dynamic`)로 남긴다.
- 실제 쿼리 실행, 웨어하우스 접속, `INFORMATION_SCHEMA` 덤프
- `map.html`에 컬럼 표시. 이번에는 `report.html`과 JSON만 바꾼다(Q12에서 다시 확인).

## 3. 접근 방식과 권장안

제약: 스킬 폴더는 표준 라이브러리만 `import`한다(`tests/test_stdlib_only.py`가 모든 `import` 문을 검사). Python 3.9에서 동작해야 한다. 따라서 sqlglot은 쓸 수 없다.

**sqlglot은 참고 구현이다.** 가져다 쓰지 않고 구조를 빌린다. 빌릴 만한 생각은 다음과 같다(코드 복사 금지, 라이선스와 크기 문제를 피한다).

- tokenizer → AST → 이름 한정(qualify) → lineage, 네 단계를 분리한다.
- `Scope`: SELECT 하나마다 "보이는 소스"(테이블, CTE, 파생 테이블)와 별칭을 모은 객체를 두고, 컬럼 참조를 가장 안쪽 scope부터 찾는다.
- `qualify_columns`: 한정자 없는 컬럼에 소스를 붙이고, 스키마(컬럼 목록)를 알면 `*`를 펼친다. 모르면 펼치지 않는다.
- `lineage(column, sql)`: 출력 컬럼 하나에서 시작해 scope를 거슬러 올라가는 노드 트리.
- 방언별 tokenizer 설정(따옴표 문자, 주석, 키워드 집합)을 표로 둔다.

### 방안 A. 지금의 가리기(mask)·키워드 방식을 넓힌다

`SELECT`와 `FROM` 사이를 괄호 깊이로 쉼표 분할하고, 각 조각에서 `AS 별칭`과 `식별자.식별자` 패턴을 정규식으로 찾는다.

- 장점: 가장 빨리 나온다. 기존 `sql_tables`의 마스커와 토큰 정규식을 그대로 쓴다. 실패해도 조용히 덜 찾을 뿐이다.
- 단점: 이름 해석(scope)이 없다. CTE 체인, 별칭 가림(alias shadowing), 서브쿼리, UNION 위치 맞추기를 할 수 없다. 한정자 없는 컬럼이 어느 소스의 것인지 모른다. `CASE WHEN … END`의 키워드와 컬럼을 가르기 어렵다. 결과의 대부분이 `inferred`나 오탐이 된다. 목표 질문 1("어떤 식을 거쳐")에 답하지 못한다.
- 판단: 테이블 lineage에서는 "고정 이름이 대부분"이라 키워드 방식이 맞았다. 컬럼은 구조가 본질이라 맞지 않는다.

### 방안 B. 작은 tokenizer + SELECT 부분집합 재귀 하강 파서 (권장)

`sql_tables`의 마스커로 주석·Jinja 태그를 지운 텍스트를 받아 토큰으로 나누고, **쿼리 식(query expression)만** 해석하는 재귀 하강 파서를 둔다. 해석 대상은 `WITH`, `SELECT … FROM … JOIN … WHERE … GROUP BY … HAVING … QUALIFY … ORDER BY … LIMIT`, 집합 연산, 서브쿼리, 식(연산자 우선순위, 함수 호출, `CASE`, `CAST`, `OVER`)이다. 그 밖의 문장(DDL 옵션, `SET`, `ALTER`)은 문장 경계(`;`)까지 건너뛴다. 해석이 끝나면 scope 해석 단계가 컬럼 참조를 소스에 붙이고, lineage 단계가 출력 컬럼별 edge를 만든다.

- 장점
  - scope를 정확히 다룬다. CTE, 별칭 가림, 서브쿼리, UNION을 처리할 수 있다.
  - 해석할 수 없는 부분은 그 문장(또는 그 SELECT 항목)만 `unsupported`로 남기고 나머지는 계속한다. 오류 복구 지점이 분명하다(`;`, 다음 SELECT 항목의 `,`, 닫는 괄호).
  - 방언 차이는 대부분 tokenizer(따옴표, `::`, `:` 경로)와 몇 개의 문법 확장(`QUALIFY`, `* EXCEPT`, `LATERAL VIEW`)에 모인다.
  - 표준 라이브러리만으로 충분하다. 1.1.0에서 Parquet Thrift 해석기를 직접 짠 것과 같은 규모의 일이다.
- 단점
  - 코드가 1,000~1,500줄 정도 늘어난다(추정). 모듈 여러 개로 나눠야 한다.
  - 식 문법의 빈틈(방언별 함수 문법: `EXTRACT(DAY FROM x)`, `TRIM(BOTH ' ' FROM x)`, `SUBSTRING(x FROM 1 FOR 2)`, `INTERVAL '1' DAY`, 람다 `x -> x + 1`)을 하나씩 메워야 한다. 모르면 "괄호 안 토큰을 모두 인자로 보는" 관대한 규칙으로 처리한다.
  - 재귀 깊이와 메모리를 신뢰할 수 없는 입력 기준으로 제한해야 한다(5·9장).
- 판단: 목표 두 질문에 답할 수 있는 가장 작은 방식이다.

### 방안 C. 방언 전체 문법을 갖춘 SQL 파서

Hive·Spark·Presto/Trino·BigQuery·Snowflake 문법 전체(DDL, DML, 스크립팅)를 해석한다.

- 장점: 정확도 상한이 가장 높다. 이후 `ALTER`, `MERGE`, `UPDATE`까지 확장하기 쉽다.
- 단점: sqlglot은 이 일에 수만 줄을 쓴다. 표준 라이브러리만으로 짜면 유지 비용이 Arche 나머지 전체보다 커진다. 대부분은 컬럼 lineage에 쓸모없는 문법이다. 테이블 lineage 설계가 "미니 파서는 방언 차이를 모두 떠안는다"며 피한 것과 같은 이유로 피한다.

### 권장: 방안 B

이유를 한 문장으로 줄이면, **컬럼 lineage는 scope 해석이 핵심이라 파서가 필요하지만, 필요한 문법은 쿼리 식 하나뿐이므로 그 부분만 해석하는 재귀 하강 파서가 정확도와 유지 비용의 균형점이다.** 테이블 lineage(`sql_tables`)는 그대로 두고, 컬럼 lineage는 그 결과(테이블 읽기·쓰기, dbt 호출)를 입력으로 재사용한다. 파서가 실패한 문장도 테이블 lineage에는 영향을 주지 않는다.

### 방언 처리

| 방언 | 1.3.0에서 다룰 것 | 다루지 않을 것 |
|---|---|---|
| 공통(ANSI) | 큰따옴표 식별자, `CAST(x AS t)`, `CASE`, 윈도 함수, `FILTER (WHERE …)` | — |
| Hive / Spark SQL | 백틱 식별자, `INSERT OVERWRITE TABLE … PARTITION (dt='…')`(파티션 컬럼은 상수 대입으로 기록), `LATERAL VIEW [OUTER] explode(x) t AS c`(생성 컬럼 `c` ← `x`, `transform`), 다중 INSERT, `DISTRIBUTE/SORT/CLUSTER BY` 건너뛰기 | `TRANSFORM … USING 'script'` |
| Presto / Trino | `x::t`가 아니라 `CAST`, `TRY_CAST`, 람다(`x -> …`), `UNNEST(arr) AS t(c)`, `WITH ORDINALITY` | — |
| BigQuery | 백틱의 `project.dataset.table`(한 덩어리), `* EXCEPT/REPLACE`, `QUALIFY`, `STRUCT`·`ARRAY` 생성자(변환으로 처리), `SAFE_CAST` | `UNNEST`의 구조체 필드 펼치기, 스크립팅 |
| Snowflake 기본 | `x::t` 캐스트, `col:field` 경로(최상위 `col`까지만), `* EXCLUDE/RENAME`, `QUALIFY`, `IFF`, 따옴표 없는 이름의 대문자 정규화(Q6) | `FLATTEN` 결과 필드, `$1` 위치 참조(스테이지 파일) |
| Jinja(dbt) | `{{ ref() }}`·`{{ source() }}`는 테이블 자리, `{{ config(...) }}`는 무시, 그 밖의 `{{ … }}`는 식 자리에서 "알 수 없는 값"(`dynamic`), `{% if %}…{% else %}…{% endif %}`는 두 분기의 SQL이 모두 남는다(지금 마스커 동작) | `{% for %}`로 만든 컬럼, 매크로 결과 |

**Jinja 주의(확인 필요).** 지금 `sql_tables.mask`는 `{% … %}` 태그만 가리고 블록 안 SQL은 남긴다. `{% if a %} x AS c, {% else %} y AS c, {% endif %}`이면 파서에는 `x AS c, y AS c,`가 보인다. 출력 컬럼 이름이 겹치므로 두 edge를 모두 남기고 `inferred`로 낮추는 규칙이 필요하다. 끝에 남는 쉼표(`… , FROM`)도 파서가 견뎌야 한다. 프로토타입에서 실제 dbt 레포(예: jaffle-shop, dbt-project-evaluator. 1.0 릴리스 노트가 이 둘로 dbt ref를 검증했다고 적었다)로 확인한다.

**토큰 재사용.** `sql_tables`의 `mask`는 줄바꿈과 글자 위치를 유지하므로 근거 줄 계산을 그대로 쓸 수 있다. 다만 `mask`는 문자열 리터럴 내용을 공백으로 바꾼다. 컬럼 lineage에서는 `'…'`가 "상수"라는 것만 알면 되므로 문제없다. `_dbt_calls`와 `_placeholders`도 재사용 후보다. 지금은 모듈 내부 함수(`_` 접두사)이므로 공개 함수로 올릴지 spec에서 정한다.

## 4. 결정해야 할 질문 목록

새 세션은 브레인스토밍에서 아래 질문을 **한 번에 하나씩** 사용자에게 묻는다. 각 질문에 선택지와 권장 기본값을 붙였다. 사용자가 "권장대로"라고 하면 기본값을 쓴다. 중요도 순서로 늘어놓았다.

### Q1. 컬럼 edge를 어디에 둘까

- (a) 새 산출물 `columns.json`을 두고 `graph.json`은 바꾸지 않는다. `inventory_sha256`으로 같은 스냅샷임을 묶는다. `imports.py`가 `graph.json` 다음에 쓴다.
- (b) `graph.json`의 `nodes`에 컬럼 노드, `edges`에 `kind: "DERIVES"` 같은 컬럼 edge를 더한다.
- (c) 새 CLI(`columns.py`)가 따로 실행되어 `columns.json`을 쓴다(`data_profile.py`처럼 선택 단계).
- **권장: (a).** 컬럼 edge는 파일 edge보다 수십 배 많을 수 있다. `graph.json`에 넣으면 지도(`atlas.py`), 감사, 파일 상세가 모두 새 kind를 견뎌야 하고, SQL이 없는 레포의 `graph.json`도 바이트 단위로 같아야 한다는 약속을 지키기 어렵다. 별도 CLI(c)는 사용자가 단계를 빠뜨리기 쉽다. SQL 파일이 하나도 없으면 `columns.json`을 쓰지 않는다. `render.py`는 `profile.json`과 같은 방식으로 읽고 스냅샷 불일치를 거부한다.

### Q2. 컬럼 edge의 상태(verified / inferred / unresolved) 규칙

- 제안 기본값(보수적으로, 과소 주장 쪽으로):
  - `verified`: 참조가 한정자(별칭·테이블)로 소스 하나에 붙고, 그 소스가 같은 파일의 CTE·파생 테이블이거나 테이블 lineage에서 `verified`로 해석된 테이블이며, 그 테이블의 컬럼 목록이 **레포 SQL에서** 알려져 있고 그 컬럼이 목록에 있다.
  - `inferred`: 한정자 없는 컬럼인데 scope의 소스가 하나뿐이다. 또는 컬럼 목록을 1.2.0 문서·`profile.json`에서 얻었다. 또는 `SELECT *` 펼치기, 위치로 맞춘 INSERT, Jinja `if` 분기, 테이블 lineage가 `inferred`. 여럿 겹치면 가장 낮은 상태를 쓴다.
  - `unresolved`: `ambiguous`(소스가 여럿이고 어느 쪽 컬럼인지 모름), `unknown_star`, `dynamic`(Jinja 값·변수 테이블), `unsupported`(파서가 해석 못 한 문법), `parse_error`.
  - 상류 테이블이 외부 테이블이면 edge는 그대로 두고 상류 노드에 `external: true`를 붙인다.
- 대안: 한정자만 있으면 컬럼 목록 확인 없이 `verified`(재현율↑, 오탐 위험↑).
- **권장: 제안 기본값.** 1.1.0의 교훈대로 `inferred`가 `verified`보다 안전하다.

### Q3. 컬럼을 모르는 소스의 `SELECT *`

- (a) 펼치지 않고 출력 쪽에 `*` 하나를 `unresolved`(`unknown_star`)로 남긴다. 하류에서 그 테이블의 컬럼을 읽으면 "출처: 상류 테이블의 같은 이름 컬럼(추정)"으로 잇는다.
- (b) 하류 SQL이 그 테이블에서 실제로 읽는 컬럼 이름을 모아 역으로 펼친다(수요 기반 추정).
- (c) 완전히 건너뛴다.
- **권장: (a)에 "같은 이름 통과" 규칙을 더한 것.** `SELECT * FROM a`로 만든 `b`에서 하류가 `b.x`를 읽으면 `a.x → b.x`를 `inferred`(`rule: star_passthrough`)로 잇는다. 하류 근거 없이 컬럼을 만들지 않는다. (b)는 근거가 흐려져 피한다.

### Q4. 기록할 식 종류(kind)

- 제안 집합: `direct`(같은 이름 그대로), `rename`(이름만 바뀜), `transform`(함수·연산·CAST·CASE 결과), `aggregate`(집계 함수 안), `window`(윈도 함수), `constant`(리터럴만으로 만든 컬럼, 상류 없음), `filter`(WHERE·HAVING·QUALIFY), `join_key`(JOIN ON·USING), `group_key`(GROUP BY), `order_key`(ORDER BY, 윈도의 PARTITION/ORDER 포함).
- `filter`·`join_key`·`group_key`·`order_key`는 출력 컬럼으로 가지 않는다. "출처" 질문에서는 빼고 "영향" 질문에서만 보인다. 대상은 "그 문장이 쓰는 테이블"로 둔다(컬럼 → 테이블 edge).
- 대안: `direct`/`transform`/`usage` 세 개만.
- **권장: 제안 집합.** CASE의 조건 컬럼(`CASE WHEN status = 'x' THEN amount END`)은 `amount`는 `transform`, `status`는 `transform`(조건)으로 둘 다 남기되 `role: "condition"`을 붙일지 spec에서 정한다.

### Q5. 컬럼 목록의 출처와 우선순위

- 후보: (1) 레포 SQL이 그 테이블을 쓰며 만든 출력 컬럼, (2) 레포의 `CREATE TABLE (…)` DDL, (3) 1.2.0 문서 컬럼, (4) 1.1.0 `profile.json`의 데이터 컬럼.
- 질문: (4)를 쓸까? `profile.json`은 `data_profile.py` 다음에만 있으므로, 쓰면 `columns.json`을 data_profile 이후에 다시 만들어야 한다.
- **권장: (1) > (2) > (3)만 쓰고, (4)는 쓰지 않는다.** `columns.json`은 imports 단계에서 결정적으로 나와야 한다. 대신 리포트에서 SQL 출력 컬럼과 데이터 컬럼의 차이를 보여 주는 비교는 render 단계에서 할 수 있다(선택, Q11). 출처가 여럿 겹치고 서로 다르면 (1)을 쓰고 차이를 `column_sources_disagree`로 기록한다.

### Q6. 대소문자와 따옴표

- (a) 따옴표 없는 이름은 소문자로, 따옴표 있는 이름은 그대로 두되 비교는 소문자로 한다. 테이블 lineage(`_name`이 모두 소문자로 바꿈)와 같다.
- (b) 방언별 규칙(Snowflake 따옴표 없는 이름 = 대문자, Presto = 소문자, BigQuery 컬럼은 대소문자 무시)을 따른다.
- **권장: (a).** 방언을 알 수 없는 레포가 대부분이고(테이블 lineage 설계도 "엔진은 확인하지 못했다"고 적었다), 테이블 이름과 같은 규칙이어야 둘이 맞는다. 표시용으로 원래 철자(`display`)를 하나 남긴다. 대소문자만 다른 두 따옴표 이름이 한 테이블에 있으면 `ambiguous`로 둔다.

### Q7. 열 목록 없는 `INSERT INTO t SELECT …`

- (a) 대상 컬럼 목록을 알면(Q5) 위치로 맞추고 `inferred`(`rule: positional`). 모르면 SELECT 별칭을 대상 컬럼 이름으로 보고 `inferred`(`rule: select_alias`).
- (b) 모르면 edge를 만들지 않는다.
- **권장: (a).** Hive `INSERT OVERWRITE`는 열 목록을 거의 쓰지 않는다. 위치와 별칭이 다르면(`SELECT a AS x`인데 대상 첫 컬럼이 `y`) 위치를 따르고 `alias_mismatch: true`를 남긴다. 개수가 다르면 `unresolved`(`reason: arity`).

### Q8. 성능 상한

- 제안: 문장 하나 토큰 200,000개, 중첩 깊이(괄호·서브쿼리·CASE) 128, SELECT 항목 2,000개, 파일당 컬럼 edge 20,000개, 전체 컬럼 edge 500,000개, 영향 BFS는 결과 5,000개에서 멈추고 `truncated: true`. 넘으면 그 문장(또는 전체)을 `degraded`/`truncated`로 기록하고 계속한다. SQL 파일 크기 상한은 기존 inventory의 1MB(`MAX_BYTES = 1_000_000`, 넘으면 `too_large`)를 그대로 따른다.
- 질문: 숫자를 어떻게 정할까? 실측 레포 기준이 필요하다.
- **권장: 제안 값으로 시작하고, 프로토타입에서 가장 큰 공개 dbt 레포와 사내 Airflow 레포(사용자가 실행)로 시간·메모리를 잰 뒤 spec에 확정한다.** 파서는 Python 재귀 한도(기본 1000)에 닿기 전에 직접 깊이 검사로 멈춰야 한다.

### Q9. `changes.py`의 컬럼 영향 범위

- (a) `--base-out`(두 스냅샷)이 있을 때만 컬럼 영향을 계산한다. base와 head의 `columns.json`을 비교해 사라진 컬럼, 새 컬럼, 정의(상류 집합·식 종류·식 텍스트 해시)가 바뀐 컬럼을 씨앗으로 삼고, 사라진 것은 base 그래프에서, 나머지는 head 그래프에서 하류로 따라간다.
- (b) 스냅샷 하나만 있을 때도, 바뀐 SQL 파일이 쓰는 모든 출력 컬럼을 씨앗으로 삼는다(거친 추정, `seed: "file"`).
- (c) (a)와 (b) 둘 다. 결과에 `seed: "column_diff" | "file"`을 남겨 구분한다.
- **권장: (c).** `changes.py`는 지금 줄 diff를 보지 않으므로 하나짜리 스냅샷에서는 컬럼 단위 차이를 알 수 없다. 정확한 답은 두 스냅샷에서만 나온다고 리포트에 적는다.

### Q10. 1.2.0 대응이 없는 dbt 모델의 출력 테이블 이름

- (a) 모델 이름(파일 stem)을 테이블 이름으로 쓰고 `inferred`.
- (b) dbt 모델은 1.2.0 대응이 있을 때만 컬럼 lineage에 넣는다.
- **권장: (a).** 1.2.0 설계에 따르면 `dbt_models[].table`은 alias를 리터럴로 알 수 없는(`dynamic: true`) 모델에만 비어 있다. 그래서 이 규칙은 그 모델에만 쓰는 안전망이다. 1.2.0이 설계대로 병합되었다면 이 질문은 "dynamic 모델을 컬럼 lineage에 넣을까"로 좁혀 묻는다.

### Q11. 리포트에 "문서 vs SQL 출력 컬럼" 비교를 넣을까

- (a) 넣는다. 1.2.0의 "문서 vs 데이터" 비교 옆에 "SQL이 만들지만 문서에 없는 컬럼", "문서에 있지만 SQL이 만들지 않는 컬럼"을 보인다.
- (b) 이번에는 뺀다.
- **권장: (b).** 범위를 지킨다. 필요하면 1.3.x로 미룬다. 1.2.0 비교 화면이 어떻게 생겼는지 확인하고 사용자에게 다시 묻는다.

### Q12. 지도(`map.html`)에 무엇을 보일까

- (a) 이번에는 보이지 않는다. (b) 테이블 카드에 컬럼 수만. (c) 컬럼 edge까지.

### Q13. 쓰기 대상이 없는 SELECT(분석용 쿼리 파일)

## 5. 산출물 형태 초안

모든 키 이름은 초안이다. spec에서 확정한다. 정렬과 중복 제거 규칙을 함께 정해 같은 입력이면 바이트 단위로 같은 파일이 나와야 한다.

### `columns.json` (Q1 권장안 기준)

```json
{
  "columns_version": 1,
  "inventory_sha256": "<graph.json과 같은 값>",
  "columns": [
    {"id": "col:billing.orders.amount", "table": "billing.orders", "column": "amount",
     "display": "amount", "known_from": ["sql_output"], "external": false,
     "defined": {"path": "dags/billing/sql/load_orders.sql", "line": 4, "quote": "o.amt AS amount,"}},
    {"id": "col:staging.orders.amt", "table": "staging.orders", "column": "amt",
     "known_from": [], "external": true}
  ],
  "edges": [
    {"from": "col:staging.orders.amt", "to": "col:billing.orders.amount",
     "kind": "rename", "status": "verified", "rule": "qualified",
     "expression": "o.amt", "via": [],
     "evidence": {"path": "dags/billing/sql/load_orders.sql", "line": 4, "quote": "o.amt AS amount,"}},
    {"from": "col:billing.orders.amount", "to": "col:mart.revenue.net_amount",
     "kind": "aggregate", "status": "inferred", "rule": "single_source",
     "expression": "SUM(amount) - SUM(r.amount)", "via": ["cte:paid"],
     "evidence": {"path": "dags/mart/sql/revenue.sql", "line": 14, "quote": "..."}},
    {"from": "col:billing.orders.status", "to": "table:mart.revenue",
     "kind": "filter", "status": "verified", "rule": "qualified",
     "evidence": {"path": "dags/mart/sql/revenue.sql", "line": 20, "quote": "WHERE o.status = 'paid'"}}
  ],
  "unresolved": [
    {"to": "col:mart.revenue.region", "spec": "region", "reason": "ambiguous",
     "candidates": ["billing.orders", "crm.customers"],
     "evidence": {"path": "dags/mart/sql/revenue.sql", "line": 9, "quote": "region,"}},
    {"to": "table:mart.wide", "spec": "*", "reason": "unknown_star", "source": "staging.events",
     "evidence": {"path": "...", "line": 3, "quote": "SELECT * FROM staging.events"}}
  ],
  "statements": [
    {"path": "dags/mart/sql/revenue.sql", "index": 0, "line": 1, "target": "mart.revenue",
     "status": "parsed | partial | unsupported | parse_error", "reason": null}
  ],
  "truncated": false
}
```

규칙 초안.

- 컬럼 id는 `col:<정규화한 테이블>.<정규화한 컬럼>`이다. 테이블 이름은 테이블 lineage의 정규화(`sql_tables._name`)와 같아야 한다. 변수 스키마(`{}.ledger`)도 그대로 쓴다.
- 파일 내부의 CTE·파생 테이블은 노드로 만들지 않는다. 지나간 경로를 `via`(`cte:<이름>`, `subquery:<줄>`)로만 남긴다. 그래서 edge는 항상 "실제 테이블 컬럼 → 실제 테이블 컬럼(또는 테이블, 또는 `query:` 가상 노드)"이다.
- `expression`은 원문(가린 텍스트가 아니라 원래 텍스트)의 해당 식을 공백 정리 후 200자에서 자른다(`MAX_QUOTE_CHARS`와 같은 값). 문자열 리터럴 값이 들어가므로 Q-목록에 "리터럴을 `'…'`로 가릴지"를 spec에서 정한다. 기본 권장은 가리지 않음(SQL은 레포 안 코드이고 이미 `quote`에 나온다).
- 파일 사이의 연결: 파일 A가 `billing.orders`를 쓰며 `amount`를 만들고, 파일 B가 `billing.orders`에서 `amount`를 읽으면 같은 노드 `col:billing.orders.amount`를 공유하므로 자동으로 이어진다. 테이블 이름 맞추기가 `inferred`(`lineage.resolve`의 `table_name` 규칙)이면 B 쪽 edge 상태를 `inferred`로 낮추고 읽은 이름과 맞춘 이름을 둘 다 남긴다(`table_rule`).
- 정렬: `columns`는 `id`, `edges`는 `(to, from, kind, evidence.path, evidence.line)`, `unresolved`는 `(evidence.path, evidence.line, spec)`.

### `changes.json` 추가 키 (Q9 권장안 기준)

```json
"column_impact": {
  "available": true,
  "seeds": [{"column": "col:staging.orders.cust_id", "change": "removed | added | redefined | file",
             "seed": "column_diff | file", "path": "dags/staging/sql/orders.sql"}],
  "affected": [{"column": "col:mart.revenue.customer_key", "depth": 2,
                "kinds": ["rename", "join_key"], "status": "inferred",
                "files": ["dags/mart/sql/revenue.sql"]}],
  "affected_files": ["dags/mart/sql/revenue.sql"],
  "affected_tables": ["mart.revenue"],
  "truncated": false
}
```

- 기존 `files[].impact`(파일 단위)는 바꾸지 않는다. 추가 키다. `SCHEMA_VERSION`은 `"1.0"` 그대로이고 `docs/artifact-compatibility.md`에 적는다.
- 경로의 상태는 지나간 edge 중 가장 낮은 상태다. `unresolved`·`unknown_star`를 지나면 "여기서 더 있을 수 있음"으로 표시한다.

### 리포트 ("Tables" 구역)

1. **테이블 블록 안의 컬럼 패널.** 1.1.0의 테이블 블록(`report_data.table_data`, profile이 있을 때)과 별개로, `columns.json`이 있으면 SQL이 쓰는 테이블마다 `<details>`를 하나 둔다(profile 블록이 있으면 그 안에 "컬럼 lineage" 하위 블록으로). 표의 열: 컬럼 이름, 출처(상류 `table.column` 링크 목록), 식 종류 배지, 식(`<code>`, 잘림), 상태 배지, 근거 링크(기존 `_evidence` 형태).
2. **"이 컬럼을 지우면" 보기.** 각 컬럼 행을 펼치면 하류 영향(깊이별 들여쓰기 목록: 하류 컬럼, `filter`·`join_key` 사용처, 파일, 테이블)을 보인다. 1.1.0처럼 JS 없이 `<details>`만 쓸지, 지연 렌더링이 필요할지 컬럼 수를 보고 정한다. 기본 제안: 하류 목록은 렌더 시점에 미리 계산해 컬럼당 50개까지 그리고 "N개 더"로 센다.
3. **따라가지 못한 컬럼.** `ambiguous`·`unknown_star`·`dynamic`·`unsupported`를 사유별로 접어 보인다(기존 "따라가지 못한 이름"과 같은 형태).
4. **안내문.** "SQL 파일의 SELECT만 읽는다. 뷰 안, Python 안 SQL, ALTER로 바뀐 이름, 매크로 결과는 따라가지 않는다. `inferred`는 확인이 필요하다."
5. **변경 구역(`_changes`).** `column_impact`가 있으면 파일 카드 아래에 "영향받는 컬럼" 목록을 더한다.
6. 테이블 하나의 컬럼 표는 200개까지 그린다(1.1.0의 `MAX_COLUMNS_SHOWN = 200`과 같게).

### SKILL.md에서 에이전트가 쓰는 법(초안)

"컬럼 X는 어디서 오나" 질문에는 `columns.json`의 `edges`에서 `to == col:T.X`를 거슬러 올라가 답하고, 각 단계의 `evidence`를 인용한다. `inferred`는 확인이 필요하다고 말한다. "C를 지우면" 질문에는 `from == col:T.C`에서 하류로 따라간다. 별도 조회 CLI를 둘지는 spec에서 정한다(기본: 두지 않음, YAGNI).

## 7. 작업 단계(태스크) 분해

1.1.0 계획(`docs/plans/2026-11-25-data-profile.md`)의 형식을 따른다. 그 계획은 태스크마다 **Files**, **Interfaces**(Consumes/Produces), 체크박스 단계(실패하는 테스트 작성 → 실행해 실패 확인 → 구현 → 통과 확인 → 커밋)를 두고, 테스트 코드와 구현 코드를 전부 적었다. 아래는 그 계획을 쓰기 위한 뼈대다. 태스크 크기는 1.1.0의 태스크(테스트 5~15개, 구현 100~400줄)와 비슷하게 잡았다.

### Task 0 (계획 전): 프로토타입

- **목표:** 임시 폴더의 레포 사본에서 `tokens`·`parser`·`scope`·`derive`를 먼저 짜 보고, 공개 dbt 레포 두 개(jaffle-shop, dbt-project-evaluator)와 `evals/fixtures/airflow-sql`에서 돌린다. 성능 상한(Q8)과 방언 빈틈 목록을 얻는다.
- **완료 기준:** spec의 상한값·지원 문법 표가 실측 숫자로 채워진다. 이 태스크는 커밋하지 않는다.

### Task 1: 토큰화 `sqlcol/tokens.py`

- **Files:** `sqlcol/__init__.py`, `sqlcol/tokens.py`, `langs/sql_tables.py`(공개 함수만), `tests/unit/test_sqlcol_tokens.py`
- **핵심 테스트:** 줄 번호 보존, 백틱·큰따옴표 식별자, `::`·`->`·`||`, 숫자(`1e3`, `.5`), 문자열 자리, `{{ ref('x') }}`가 테이블 토큰 하나가 됨, `{{ var('x') }}`가 동적 값 토큰, `{% if %}` 태그 제거 후 내부 SQL 유지, 주석 안의 `SELECT` 무시
- **완료 기준:** 기존 `test_sql_tables.py`가 그대로 통과하고, 새 테스트가 통과한다.

### Task 2: AST와 식 파서

- **Files:** `sqlcol/ast.py`, `sqlcol/parser.py`(식 부분), `tests/unit/test_sqlcol_expr.py`
- **핵심 테스트:** 연산자 우선순위, 함수 호출(`COUNT(DISTINCT x)`, `COUNT(*)`), `CASE` 두 형태, `CAST`·`::`·`TRY_CAST`·`SAFE_CAST`, 윈도 `OVER (…)`·`FILTER (WHERE …)`, `EXTRACT(DAY FROM x)`·`TRIM(BOTH ' ' FROM x)`, `INTERVAL`, 람다, `col:field`, 모르는 구문은 `Unknown`이 되어 내부 컬럼 참조만 모음, 깊이 상한 초과 시 `ParseError`(재귀 한도에 닿지 않음)
- **완료 기준:** 식 하나를 넣으면 노드 트리와 그 안의 컬럼 참조 목록이 나온다.

### Task 3: 쿼리·문장 파서

- **Files:** `sqlcol/parser.py`(쿼리·문장), `tests/unit/test_sqlcol_parser.py`
- **핵심 테스트:** `WITH` 체인·열 목록 CTE·`RECURSIVE`, 서브쿼리, JOIN 종류·`USING`, `LATERAL VIEW`, `UNNEST … AS t(c)`, 집합 연산, `QUALIFY`, `* EXCEPT/REPLACE/EXCLUDE`, `INSERT … (cols) SELECT`, `INSERT OVERWRITE TABLE t PARTITION (…)`, `CREATE TABLE AS`, `CREATE TABLE (c type)`, `CREATE VIEW`, 문장 여러 개, 실패한 문장 다음 문장은 정상 해석, 토큰 상한
- **완료 기준:** 문장마다 `{target, columns(열 목록), query}`와 `status`가 나온다.

### Task 4: scope 해석

- **Files:** `sqlcol/scope.py`, `tests/unit/test_sqlcol_scope.py`
- **핵심 테스트:** 별칭 가림(CTE 이름이 실제 테이블 이름을 가림, 안쪽 별칭이 바깥 별칭을 가림), 상관 서브쿼리의 바깥 참조, 한정자 없는 컬럼의 소스 하나·여럿·컬럼 목록으로 결정, `USING` 컬럼, `*`·`t.*` 펼치기(목록 있음·없음), `EXCEPT` 적용, SELECT 별칭을 `GROUP BY`·`ORDER BY`에서 참조(방언 차이: 허용하되 `inferred`)

## 8. 테스트와 평가

### 단위 테스트 주제

- 토큰화: 위치 보존, 방언별 따옴표·연산자, Jinja 처리
- 식 파서: 우선순위, 함수 특수 문법, 모르는 구문 복구, 깊이 상한
- 문장 파서: 쓰기 머리 각 형태, 쿼리 식 각 절, 문장 경계 복구
- scope: 가림, 상관 서브쿼리, 한정자 없는 컬럼, 펼치기
- 유도: kind 분류, 위치 맞추기, `via`
- 파일 사이: 우선순위, 상태 낮추기, 반복, 결정성
- 영향: BFS, 비교, 상한
- 리포트: 이스케이프, 상한, 없는 경우
- 적대적 입력: 괄호 10만 개, 아주 긴 한 줄, 닫히지 않은 따옴표·Jinja, 깊이 1만의 `CASE` 중첩, 같은 CTE 이름 반복. 모두 시간·메모리 상한 안에서 `degraded`로 끝나야 한다.

### 새 fixture `evals/fixtures/column-lineage/`

`evals/fixtures/airflow-sql/`과 같은 형태(`repo/`와 정답 파일)로 둔다. `evals/score.py`는 `expected_graph.json`이 있는 폴더만 읽으므로, 이 fixture에 `expected_graph.json`을 두지 않으면 기존 채점기는 건너뛴다(1.1.0 `data-profile` fixture와 같은 방식). 정답 파일 이름은 `expected_columns.json`을 제안한다. 모두 합성이며 사내 코드를 넣지 않는다.

정답은 **구현 전에 손으로** 적는다. 담아야 할 함정 사례는 다음과 같다.

| 사례 | 내용 | 정답에서 볼 것 |
|---|---|---|
| 별칭 가림 | CTE 이름 `orders`가 실제 테이블 `billing.orders`를 가림. 안쪽 서브쿼리 별칭 `o`가 바깥 `o`를 가림 | edge가 CTE를 지나 올바른 실제 테이블로 감 |
| CTE 체인 | `a → b → c` 세 단계, 중간에 이름 변경과 집계 | 최종 edge 하나에 `via: [cte:a, cte:b, cte:c]`, kind는 가장 강한 것(`aggregate`) |
| `SELECT *` 펼치기 | 컬럼을 아는 소스(같은 레포의 CTAS), 모르는 소스(외부 테이블), `* EXCEPT (x)` | 아는 것은 펼침(`inferred`), 모르는 것은 `unknown_star`, 하류 읽기로 `star_passthrough` |
| 한정자 없는 모호한 컬럼 | JOIN 두 소스, 둘 다 컬럼 목록 모름 / 한쪽만 앎 / 둘 다 앎 | `ambiguous`(후보 둘) / 앎 쪽이 가지면 `inferred` / 정확히 한쪽이면 `verified` |
| UNION | 분기 셋, 첫 분기 별칭이 이름, 둘째 분기 상수 | 위치마다 분기별 edge, 상수 분기는 `constant` |
| 윈도 함수 | `ROW_NUMBER() OVER (PARTITION BY cust ORDER BY ts)`, `SUM(amt) OVER (…)` | `cust`·`ts`는 `order_key`(사용처), `amt`는 `window` |
| CASE | 조건 컬럼과 결과 컬럼이 다름, `ELSE NULL` | 둘 다 상류, 조건 쪽 표시(Q4 결정에 따름) |
| 필터·조인 키 | `WHERE status = 'paid'`, `JOIN … ON o.cust_id = c.id` | `filter`, `join_key` 사용처 edge |
| 열 목록 없는 INSERT | Hive `INSERT OVERWRITE TABLE t SELECT a, b AS y`, 대상 DDL 있음 | 위치 맞춤, `alias_mismatch` |
| Jinja | dbt 모델에 `{{ ref() }}`, `{{ source() }}`, `{% if target.name == 'prod' %}` 분기, `{{ var('x') }}` 컬럼 | 분기 둘 다 `inferred`, `var` 컬럼은 `dynamic` |
| 파일 사이 | A가 CTAS로 `stage.x` 생성, B가 `stage.x`를 읽어 `mart.y` 생성, C가 `mart.y`에서 `SELECT *` | A → B → C 체인, C는 B의 출력 목록으로 펼침 |
| 변수 스키마 | `{{ params.schema }}.ledger`를 읽고 쓰기 | 테이블 lineage가 `inferred`이므로 컬럼도 `inferred` |
| 해석 불가 | `PIVOT`, 저장 프로시저 블록 | `unsupported` 문장, 다음 문장은 정상 |
| 변경 영향 | `base/`와 `head/` 두 판(컬럼 이름 변경 하나, 삭제 하나) | `column_impact`의 정답 목록 |

변경 영향 사례는 `changes.py`가 Git 저장소를 요구하므로, 채점기가 임시 폴더에 두 커밋을 만들어 실행한다(확인 필요: `tests/unit/test_changes_cli.py`가 이미 이렇게 하는지 보고 같은 도우미를 쓴다).

### 채점기 `evals/score_columns.py`

- **정밀도·재현율 게이트**: `verified` 컬럼 edge(`from`, `to`, `kind`)만 센다. `evals/score.py`의 IMPORTS 채점과 같은 원칙이다. 정답에서 `inferred`로 표시한 edge를 스크립트가 `verified`로 내면 오탐으로 센다(과대 주장 벌점).
- **정확 비교**: `inferred` edge 집합, `unresolved`(사유, 후보), 문장 상태, `column_impact`는 집합으로 정확히 비교한다.
- **시작 임계값 제안**: `verified` 정밀도 0.98 이상, 재현율 0.90 이상(`score.py`의 기본값은 정밀도 0.98, 재현율 0.95다. 컬럼은 처음에 재현율을 조금 낮춰 시작하고, 1.3.x에서 0.95로 올린다). `inferred` 쪽 정밀도는 게이트 없이 보고만 한다. 임계값은 `--min-precision`, `--min-recall`로 바꿀 수 있게 둔다.
- `ci.yml`의 `evals/score_profile.py` 다음 단계에 넣는다.

### Python 3.9 호환

- `match` 문, 런타임 `X | Y` 타입 표기, 3.10 이상 API(`itertools.pairwise`, `zip(strict=True)`, `int.bit_count` 등)를 쓰지 않는다.
- 태스크마다, 그리고 릴리스 전에 다음을 실행한다.

```bash
uv run --no-project --python 3.9 --with pytest python -m pytest -q -p no:cacheprovider
```

- 전체 테스트(`python3 -m pytest -q`), `python3 evals/score.py`, `python3 evals/score_profile.py`, `python3 evals/score_columns.py`가 모두 통과해야 한다.
- `tests/test_stdlib_only.py`가 새 모듈도 검사한다. 별도 조치는 필요 없다.

## 11. 1.1.0에서 얻은 교훈

- **계획 전에 프로토타입한다.** 1.1.0 계획은 "이 계획의 모든 코드와 테스트는 임시 폴더의 레포 사본에서 구현해 실행했다"고 적었다. 1.3.0도 Task 0에서 파서 핵심을 임시 사본에 먼저 짜 보고, 그 결과로 spec의 숫자와 지원 표를 채운 뒤 계획을 쓴다.
- **태스크마다 리뷰한다.** 1.1.0의 태스크별 리뷰가 실제 버그를 잡았다. 예: 신뢰할 수 없는 입력을 읽는 해석기의 메모리 폭주, 허용 목록 변경 뒤 민감 이름을 조용히 더 이상 잡지 못한 문제(커밋 로그의 "Restore substring matching for long sensitive words", "Match sensitive names as substrings after removing known harmless words"가 그 흔적이다). 컬럼 파서는 같은 종류의 위험(적대적 입력, 규칙 변경으로 인한 조용한 회귀)이 크다.
- **출력은 결정적으로.** 같은 입력이면 바이트 단위로 같은 JSON. 시간·환경 정보는 `run.json`에만.
- **보수적인 상태를 고른다.** 애매하면 `verified`보다 `inferred`, `inferred`보다 `unresolved`. 채점기도 과대 주장을 벌점으로 센다.

## 12. 신규 세션 시작 방법

1. **worktree 만들기.** 1.2.0이 `main`에 병합됐는지 확인한다(`git fetch origin && git log origin/main --oneline | head`, 1.2.0 병합 커밋과 `__version__`이 `1.2.0`인지). 병합 전이면 사용자에게 알리고 멈춘다. 병합됐으면 `origin/main`에서 새 브랜치의 worktree를 만든다(예: `erkoo/column-lineage-impl`. 이름은 사용자에게 확인). 이 브리프는 1.2.0 브랜치(`erkoo/dbt-docs`)에 함께 커밋되어 1.2.0과 같이 `main`에 들어간다. `main`에 없으면 그 브랜치에서 가져온다.
2. **읽기.** 이 브리프, 그리고 다음 파일을 읽는다.
   - `skills/arche/SKILL.md`
   - `docs/specs/2026-11-23-table-lineage-design.md`, `docs/specs/2026-11-25-data-profile-design.md`, 1.2.0 spec
   - `skills/arche/scripts/arche_lib/langs/sql_tables.py`, `lineage.py`, `graph.py`(`_reads`, `_written_table_list`, `_dbt_edges`), `dbt.py`, `langs/yaml_dbt.py`와 1.2.0이 더한 메타데이터 모듈
   - `skills/arche/scripts/arche_lib/changes.py`, `scripts/changes.py`, `report.py`(`_tables`, `_changes`), `report_data.py`, `scripts/render.py`, `scripts/imports.py`
   - `docs/artifact-compatibility.md`, `docs/release-notes.md`, `evals/score.py`, `evals/score_profile.py`, `evals/fixtures/airflow-sql/`
   - `docs/plans/2026-11-25-data-profile.md`(계획 형식), `tests/test_stdlib_only.py`
3. **브레인스토밍.** `superpowers:brainstorming` 스킬을 호출한다. 4장의 질문을 **한 번에 하나씩** 묻는다. 먼저 0장의 1.2.0 산출물 확인 결과를 알리고, 그다음 Q1, Q2, Q3 순서로. 사용자가 권장안을 받아들이면 다음 질문으로 넘어간다.
4. **프로토타입.** 7장 Task 0을 임시 사본에서 한다. 결과(실측 시간·메모리, 해석 실패 사유 통계)를 사용자에게 보고한다.
5. **spec 쓰기.** `docs/specs/YYYY-MM-DD-column-lineage-design.md`(날짜는 작성일). 1.1.0 spec과 같은 한국어 문체(평서문 "~다", 표 위주, "왜 바꾸는가 / 목표와 범위 / 전제 / 구성 요소 / … / 테스트 / 문서와 버전 / 이후 단계로 미루는 것")를 따른다. 사용자 검토를 받는다.
6. **plan 쓰기.** `superpowers:writing-plans` 스킬로 `docs/plans/YYYY-MM-DD-column-lineage.md`. 1.1.0 계획처럼 Global Constraints, File Structure, 태스크별 Files/Interfaces/체크박스 단계와 전체 테스트·구현 코드를 적는다.
7. **구현.** `superpowers:subagent-driven-development`로 태스크마다 서브에이전트가 구현하고, 태스크마다 리뷰한다. 리뷰에서 나온 수정은 그 태스크 안에서 끝낸다.
8. **마무리.** 10장 체크리스트, `superpowers:finishing-a-development-branch`.

**프로젝트 관례.**

- 커밋 메시지는 영어 한 문장이다. `Co-Authored-By` 줄을 붙이지 않는다.
- 사용자는 한국어로 쓴다. 답변과 문서는 한국어로 쓴다(코드·커밋 메시지·영문 산출물 문구는 영어).
- 스킬 폴더는 표준 라이브러리만, Python 3.9 이상.
- 대상 레포는 읽기만 한다. 출력 폴더는 레포 밖이다.
- 공유 git stash를 쓰지 않는다(다른 worktree와 함께 쓰므로). 작업을 잠시 치울 때는 WIP 커밋을 쓴다.
- 푸시·태그·PR 생성은 사용자가 요청할 때만 한다.
