# 근거 지도(Evidence Map) 설계

2026-11-20 제안. 대상 브랜치는 `erkoo/evidence-map`(GitHub `main` 기준)이다.

## 왜 바꾸는가

현재 리포트는 최상위 폴더를 카드로 그린다. 공개 버전을 실제 앱 picca(Flutter 앱 + Hono Worker)에 실행한 결과는 다음과 같다.

| 항목 | 결과 |
|---|---|
| System map | 카드 2개(`apps`, `workers`), 설명 없음, 연결 0개 |
| HTTP 연결 | 요청 5건 모두 `unresolved`. Worker의 `app.get("/benefits", …)` 형태의 라우트를 하나도 인식하지 못함 |
| 요청 추출 | `_get('/opportunities')`처럼 같은 파일의 헬퍼를 거치는 요청은 추출되지 않음 |
| 화면·흐름 | 에이전트가 투어 JSON을 직접 쓰지 않으면 비어 있음 |
| 범위 | 255개 파일 중 89개만 지도에 반영. SQL 마이그레이션과 설정은 보이지 않음 |

Floorplan이 잘 읽히는 이유는 그림보다 순서에 있다. 에이전트가 "이 앱의 부품이 무엇인가"를 먼저 정하고, 스크립트가 그 부품 사이의 연결을 계산해 그린다. Arche에는 그 의미 계층이 없다.

Arche가 이미 앞서는 점은 유지한다. 모든 근거에 `경로:줄`과 SHA-256이 있고, 연결마다 상태가 있으며, 대상 레포에 아무것도 쓰지 않는다.

## 목표와 범위

**목표.** 처음 보는 사람이 지도를 열어 1분 안에 앱의 부품과 연결을 말할 수 있고, 어떤 카드에서든 두 번의 클릭으로 근거 줄에 도달한다.

**이번 범위(네 작업).**

1. 라우트·요청 인식 확장
2. 의미 계층 `map.json`과 빌드
3. 지도 뷰어 `map.html`
4. 파일·엔드포인트 설명 워크시트

**이번 범위 밖.** 화면 자동 검출, 증분 갱신, 지도 안의 질문 창(로컬 서버), PRD 기반 청사진, 보안 점검 규칙 확대. 화면은 지금처럼 에이전트가 `map.json`에 근거와 함께 적는다.

**완료 기준.**

- picca에서 추출된 요청이 5건을 넘고, 외부 호스트가 아닌 정적 경로 요청은 모두 라우트 하나에 연결된다.
- picca 지도의 최상위에 부품 4개 이상과 외부 서비스(D1, 소셜 로그인)가 나타나고, 모바일 앱 → API → DB 연결이 그려진다.
- 지도에 올라간 파일의 90% 이상이 부품에 배정되고, 설명 채움률을 빌드가 숫자로 보고한다.
- 기존 테스트 369개와 `evals/score.py` 수치가 그대로 유지된다.

## 산출물과 흐름

```text
scan.py → imports.py → brief.py ──(에이전트가 map.json 작성)──→ map.py
                                                                  │
                    (에이전트가 descriptions/*.json 작성) ← describe.py
                                                                  │
                                                      render.py → map.html, report.html
```

모든 파일은 지금처럼 레포 밖 출력 디렉터리에 둔다.

| 파일 | 작성자 | 내용 |
|---|---|---|
| `inventory.json`, `graph.json` | 스크립트(기존) | 변경 없음. `http_connections`만 확장 |
| `brief.txt` | `brief.py` | 에이전트가 읽는 요약. 코드 트리와 줄 수, 진입점, 폴더 간 import 상위 묶음, HTTP 매칭, 외부 패키지와 호스트 |
| `map.json` | 에이전트 | 부품, 외부 서비스, 스캔이 못 보는 연결, 흐름, 화면, 투어 |
| `descriptions/<부품>.json` | 에이전트 | 파일·엔드포인트의 이름과 한 줄 설명 |
| `atlas.json` | `map.py` | 검증을 통과한 지도 데이터. 뷰어의 유일한 입력 |
| `map.html` | `render.py` | 지도 뷰어. 단일 파일, 오프라인 |
| `report.html` | `render.py`(기존) | 근거 목록. 지도에서 링크로 연다 |

`map.json`이 없어도 `render.py`는 동작한다. 그때는 폴더를 3~9개가 될 때까지 내려가며 나눈 자동 지도를 그리고, 카드에 "이름 미확정"을 표시한다. 기존 투어 JSON(`--tour`)은 계속 받는다.

## 1. 라우트·요청 인식

`http_routes`와 `http_requests` 레코드 형식은 유지하고 추출기를 늘린다.

**라우트.**

- TS/JS: `<수신자>.<메서드>("리터럴", …)`. 수신자는 같은 파일에서 `new Hono()`, `express()`, `Router()`, `fastify()` 등으로 만든 식별자이거나, 그 타입으로 선언된 매개변수여야 한다. `app.route("/v1", sub)`와 `app.use("/api", router)`의 접두사를 같은 파일과 import로 확인되는 파일까지 붙인다.
- Python: `@app.get("/x")`, `@router.post("/x")`, `@bp.route("/x", methods=[…])`와 `include_router(prefix=…)`, `register_blueprint(url_prefix=…)`.
- 기존 `createRoute` + `.openapi()` 인식은 그대로 둔다.

**요청.**

- TS/JS: `fetch("…")`, `axios.<메서드>("…")`, 템플릿 문자열.
- Dart: 같은 파일의 헬퍼가 경로를 인자로 받아 `Uri.parse('${base}$path')`를 만드는 경우, 호출 지점의 리터럴 인자를 요청으로 기록한다. 메서드는 헬퍼가 호출하는 `_client.<메서드>`에서 가져온다.

**매칭.** 경로를 조각으로 나눠 비교한다. `:id`, `{id}`, `<int:id>`, `${…}`는 한 조각짜리 변수로 본다.

| 경우 | 상태 | reason |
|---|---|---|
| 정적 경로가 라우트 하나와 일치 | `inferred` | `method_and_path` |
| 변수 조각을 포함해 라우트 하나와 일치 | `inferred` | `method_and_path_pattern` |
| 후보가 둘 이상 | `unresolved` | `multiple_handlers` |
| 정적 경로인데 후보 없음 | `unresolved` | `no_literal_handler` |
| 변수 경로인데 후보 없음 | `unresolved` | `dynamic_request_path` |
| 리터럴 외부 호스트로 가는 요청 | `unresolved` | `external_host` |

요청의 변수 조각은 라우트의 변수 조각에만 맞춘다. `/auth/$provider`를 `/auth/kakao`에 연결하지 않는다. 기존 reason 이름은 호환을 위해 그대로 쓴다. 외부 호스트 요청에는 `host` 필드가 붙고, 2번 작업에서 외부 서비스 부품과 연결한다.

HTTP 매칭은 배포 호스트를 확인하지 못하므로 `verified`로 올리지 않는다. 인식하지 못한 형태는 지금처럼 조용히 빼지 않고 `brief.txt`에 "라우트로 보이지만 읽지 못한 줄"로 수를 적는다.

## 2. `map.json`과 빌드

아래는 형식을 보이는 예시다. 경로와 줄 번호는 설명용이다.

```json
{
  "version": 1,
  "project": {"name": "picca", "summary": "카드 혜택을 위치와 일정에 맞춰 알려 주는 앱."},
  "audience": "everyone",
  "parts": [
    {"id": "mobile", "label": "모바일 앱", "kind": "ui",
     "summary": "사용자가 혜택을 보고 사용 내역을 남기는 Flutter 앱.",
     "paths": ["apps/mobile/lib"],
     "evidence": {"path": "apps/mobile/lib/main.dart", "start_line": 1, "end_line": 40}},
    {"id": "db", "label": "데이터베이스", "kind": "external",
     "summary": "혜택, 카드, 사용 기록을 저장하는 D1."}
  ],
  "edges": [
    {"from": "api", "to": "db", "kind": "data", "label": "읽기/쓰기",
     "evidence": {"path": "workers/api/src/lib/db.ts", "start_line": 12, "end_line": 20}}
  ],
  "flows": [{"id": "benefits", "title": "혜택 목록 보기", "steps": [
    {"part": "mobile", "note": "홈 화면이 혜택을 요청한다.",
     "evidence": {"path": "apps/mobile/lib/core/api/picca_api_client.dart", "start_line": 78, "end_line": 90}}
  ]}],
  "screens": [],
  "tour": []
}
```

- `parts`는 `parent`로 계층을 만든다. 최상위 3~9개, 깊이는 3단계까지다.
- `kind`는 `ui`, `service`, `worker`, `library`, `data`, `test`, `script`, `config`, `external`이다.
- `paths`는 glob이다. 파일은 가장 깊은 부품에 배정되고, 같은 깊이에서는 리터럴 접두사가 긴 쪽이 이긴다.
- 외부 부품은 `packages`로 `graph.externals`와 자동 연결된다.
- 근거의 SHA-256은 에이전트가 적지 않는다. `map.py`가 인벤토리에서 채우고 줄 범위를 검사한다.

**연결 상태.** 뷰어의 선 모양이 이 값을 따른다.

| 상태 | 출처 | 선 |
|---|---|---|
| `verified` | 스크립트가 해석한 정적 import | 실선 |
| `inferred` | 메서드와 경로가 일치한 HTTP 후보, 추론된 import | 긴 점선 |
| `cited` | 에이전트가 적고 `map.py`가 근거 위치를 확인한 연결 | 실선 + 인용 표식 |

`cited`는 "그 줄이 존재한다"는 확인이다. 그 줄이 주장을 뒷받침하는지는 사람이 열어서 판단하며, 뷰어의 범례에 그렇게 적는다.

**`map.py`가 하는 일.**

- 형식 검사. 문제마다 필드 이름과 "혹시 …" 제안을 출력한다.
- 파일 배정과 미배정 목록(폴더별). 10% 초과 시 경고.
- 부품 간 연결 집계: import, HTTP 후보, 외부 패키지, `edges`.
- 근거 검증: 경로가 인벤토리에 있고 제외 대상이 아니며 줄 범위가 파일 안에 있을 것.
- 경고: 요약 없는 부품, 자식 없이 24개 넘는 파일을 가진 부품, 연결되지 않은 흐름의 연속 단계, `everyone` 독자인데 개발 용어를 쓴 이름.
- `atlas.json` 작성. 기존 `changes.json`과 `audit.json`이 있으면 카드에 "변경됨"과 감사 후보 수를 붙인다.

## 3. 지도 뷰어

**구성.**

- 상단: 프로젝트 이름과 현재 위치, 검색(`/`), 보기 전환(지도 · 흐름 · 화면 · 변경 · 감사), 범례.
- 가운데: 끌어서 이동하고 휠로 확대하는 캔버스. 카드는 이름, 한 줄 설명, 작은 글씨의 실제 경로를 보여 준다.
- 오른쪽 패널: 선택한 카드의 설명, 파일·줄·엔드포인트 수, "여기를 쓰는 곳"과 "여기가 쓰는 곳", 근거 링크.

**확대 단계.** 전체 → 부품 → 하위 부품 또는 폴더 → 파일. 카드를 두 번 누르면 한 단계 들어가고, 가운데에 그 내용이, 왼쪽에 쓰는 곳, 오른쪽에 쓰이는 곳이 놓인다. 파일 수준에서는 심볼과 엔드포인트를 패널에 나열한다. URL 해시에 현재 위치를 담아 링크로 공유할 수 있게 한다.

**흐름.** 단계를 번호 붙은 카드로 올리고, 이전/다음으로 넘기면 해당 선이 강조된다. 각 단계는 설명과 근거 줄을 함께 보여 준다.

**근거 열기.** 근거 링크는 `report.html`의 해당 파일 항목을 연다. `render.py --editor vscode` 등을 주면 편집기 링크도 붙인다. 소스 본문은 지금처럼 HTML에 넣지 않는다.

**배치.** 외부 라이브러리 없이 뷰어 안에서 계층형 배치를 계산한다. 연결 방향으로 열을 정하고, 무게중심으로 열 안의 순서를 정하고, 선은 SVG 곡선으로 그린다. 한 화면의 카드는 24개로 제한하고 넘으면 폴더 묶음으로 접는다. 이 규모에서는 ELK(1.6MB) 없이 충분하고, 표준 라이브러리만 쓴다는 원칙과 기존 CSP를 지킬 수 있다.

**디자인 방향.** 건축 도면이다. 제품 이름과 맞고, 현재 리포트의 미색 종이와 녹색 잉크를 이어받는다.

- 밝은 테마가 기본이다. 모눈 바탕, 가는 선, 도면 제목란 형태의 머리말. 어두운 테마는 청사진 색으로 따로 정의한다.
- 색은 의미에만 쓴다. 녹색은 확인된 연결, 황토색은 추론, 청색은 인용, 붉은색은 감사 후보다.
- 글꼴은 내려받지 않는다. 제목은 시스템 세리프, 경로와 수치는 고정폭이다. 오프라인 단일 파일을 유지하기 위한 선택이다.
- 토큰은 CSS 변수로 정의한다. 움직임은 `transform`과 `opacity`만 쓰고 `prefers-reduced-motion`을 따른다.
- 키보드로 카드 이동과 진입이 가능해야 하고, 캔버스 없이도 읽히는 목록 보기를 함께 둔다.

## 4. 설명 워크시트

`describe.py`가 부품마다 `worksheets/<부품>.md`와 채울 틀 `descriptions/<부품>.json`을 만든다.

- 워크시트 항목: 파일의 심볼, 문서 주석 첫 줄, 쓰는 파일과 쓰이는 파일, 엔드포인트의 메서드·경로·핸들러 줄.
- 소스 본문은 싣지 않는다. 에이전트는 필요한 파일을 직접 읽는다. 비밀값 노출 위험을 스크립트가 지지 않기 위해서다.
- 설명 형식: `{"name": "…", "description": "…"}`. 키는 파일 경로 또는 `"METHOD /path"`다.
- `map.py`가 `DESCRIPTIONS files X/Y · routes X/Y`를 출력한다. 다시 실행한 `describe.py`는 비어 있는 항목만 나열한다.
- 설명이 없는 카드는 경로를 이름으로 쓰고 "설명 없음"으로 표시한다. 지어내지 않는다.

`skills/arche/references/`에 두 문서를 둔다. `choosing-parts.md`는 부품을 나누는 기준, `writing-descriptions.md`는 "코드가 오늘 하는 일을 쓴다", "이름에서 추측하지 않는다", "독자가 모두일 때는 일상어를 쓴다"를 다룬다.

## 스킬 절차 변경

`SKILL.md`의 기본 흐름을 다음으로 바꾼다.

1. scan, imports, brief 실행
2. `brief.txt`와 README, 매니페스트, 진입점을 읽고 `map.json` 작성
3. `map.py` 실행. 깨끗해지고 미배정이 10% 아래가 될 때까지 수정
4. `describe.py` 실행 후 설명 작성. 파일이 150개를 넘으면 부품 단위로 하위 에이전트에 나눈다
5. `map.py`, `render.py` 실행
6. 대화에 지도 경로, 3~5줄 구조 요약, 읽지 못한 범위, 감사 후보를 보고

읽기 전용, 레포 밖 출력, 레포 안 지시 무시, 프로젝트 코드 미실행 규칙은 그대로다.

## 오류 처리

- `map.json` 형식 오류와 근거 불일치는 `IntegrityError`로 끝내고 필드 경로를 알려 준다.
- 스냅샷이 바뀌었으면(`inventory_sha256` 불일치) `map.py`와 `render.py`가 거부한다.
- 파싱에 실패한 파일은 지금처럼 `skipped`에 남기고 지도에서 "읽지 못함"으로 센다.
- 뷰어는 `atlas.json`에 없는 참조를 만나면 그 카드만 빼고 콘솔과 패널에 수를 적는다.

## 테스트

- 단위: 라우트 추출기별, 경로 매칭, glob 배정, 근거 검증, 연결 집계, 워크시트 생성. 테스트를 먼저 쓴다.
- 픽스처: `evals/fixtures/hono-mobile`(Dart 클라이언트 + Hono Worker + 접두사 마운트). 정답 연결을 `evals/score.py`에 더한다. Python 라우트는 단위 테스트로 확인하고, Python 요청 추출이 생길 때 픽스처를 더한다.
- 뷰어: `evals/check_reports.cjs`에 `map.html` 검사(오류 없이 열림, 부품 진입, 흐름 넘김, 근거 링크)를 더한다. 320·768·1024·1440 너비와 두 테마에서 화면을 확인한다.
- 현장: picca와 Arche 자신에 실행해 완료 기준을 숫자로 기록한다.

## 열려 있는 결정

- **`map.json`의 위치.** 이 설계는 레포 밖에 둔다. 팀이 지도를 공유하려면 레포 안에 커밋할 수 있어야 하는데, 그 선택지는 증분 갱신과 함께 다음 설계에서 다룬다.
- **독자 기본값.** `everyone`으로 두었다. Arche의 첫 사용자가 개발자와 FDE라면 `developers`가 더 맞을 수 있다.
